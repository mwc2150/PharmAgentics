## What was built

- **H1 schema** (`eval/harness/cases.py`). `Finding.cut` (`plan:<id>`, `channel:<name>` or `segment:<name>`, validated: any other prefix or an empty name is refused). `Fact.needs` and `Finding.needs` (`plan_cut`, `segment_pct`, `restatement`, `national_card`). `expectations()` carries `needs` on each key fact and `cut` and `needs` on each finding (findings by `model_dump`). `python -m eval check` validates the golden set with both fields.
- **H2 cut matching** (`eval/harness/scorers.py`). `finding_recall` and `false_drivers` compare territory and cut (case and edge space ignored; a missing `cut` key, None or empty text is "no cut"). A finding with a cut is met only by a card with the same territory and cut; one without only by a card with no cut. `false_drivers` holds a cut card to the finding with the same cut, and a card whose (territory, cut) has no finding adds nothing, as before for territories. `finding_counts` is new and is what the pooled finding recall uses.
- **H2 card builders.** Both engines build every story card in `src/pharmagentics/tools/memo.py` (`story_card`, `competitor_card`) and `src/pharmagentics/tools/promotion.py` (the promotion-review card), so both got `"cut": None`. None of the files the other agent edits (`pipeline.py`, `briefing_agent/__init__.py`, `investigate.py`, `worker.py`, `briefing_lowcode/team.py`) was touched. No new cards, no change to any brief's text. The leader view's `CARD_FIELDS` allow-list is unchanged, so `cut` does not reach leaders (`tests/test_charts.py` asserts that key set).
- **H3 targets** (`scorers.TARGETS = {"key_fact_recall": 0.85, "finding_recall": 0.90}`). `run.pooled_metrics` (called where `_pooled_key_facts` was) logs, for the Briefing cases: `key_fact_recall_pooled`, `key_fact_target_met`, `finding_recall_pooled` (points over possible points across all cases; a case that never answered or has no story cards counts its possible points with none earned), `finding_target_met` (1.0 or 0.0) and `over_word_budget` (cases over either view's budget). All report-only. `_pooled_key_facts` is unchanged.
- **H4 word budget** (below). `brief_words` still returns the analyst view's count as its value; its rationale now adds the leader view's count and both budgets, and names a view that is over. `count_words` and `leader_words` are public helpers (the leader count runs the server's own `views.leadership_sections`). FR-021: `scorers.GATED_WHEN_REVIEWED = ("key_fact_recall", "finding_recall", "over_word_budget")` is the hook; `GATED` is unchanged, so nothing is gated now. When FR-006 moves the two recalls into `GATED`, `over_word_budget` joins them (a test checks the two tuples are disjoint today).
- **H5 insights and the Evaluation page.** `insights.build(..., needs=...)` adds `below_target` and `targets`: for the latest run of each system (controls `reference` and `naive_llm` left out), each case under 0.85 key-fact recall or 0.90 finding recall, with the missing fact or finding IDs read from the scorer's rationale (the assessments table's `rationale` column; a store without it is read as before) and grouped under the capability the golden file tags ("needs plan cut: ...") or "missed". `render_md` has a "Below target" section; `python -m eval insights` passes `golden_needs(cases)`. The telemetry export adds `targets` to the cases block and, only on a row under target, `below: [{scorer, score, target, needs: {capability: count}, missed: count}]`. Counts only: no fact or finding ID leaves the store. `Telemetry.tsx` shows the targets in the per-case note and, under a below-target case's name, one amber line per score (for example "Key facts found 50%, target 85% · needs plan cut: 1 · missed: 2").
- `eval/README.md`: the `key_fact_recall`, `finding_recall` and `brief_words` rows now describe the pooled metrics, cuts and budget.

## Fix outside packet H, in the same branch

`golden_number_recall` failed for the Forecast golden case CA-Q1 once the DuckDB exists (`_exacts` then has exact values): `_golden_stated` let a fact written "1" (`actual_is_provisional`) back the golden "0.656", because `same()` rounds to the coarser of the two figures. The written figure now backs a golden number only when it is at least as precise (`written.decimals >= g.decimals`). Regression test `test_a_coarser_fact_does_not_back_a_finer_golden_number` in `eval/tests/test_exact_values.py`. Without a DuckDB the exact values are skipped, which is why it did not show in a no-data run.
